1. PROJECT OVERVIEW
================================================================================

This is the Firebase Cloud Messaging (FCM) push notification setup for the TBT
(Tamil Business Tribe) Flutter app on Android.

It has two parts:

  a) Flutter app (mobile client)
     - Initializes Firebase and FCM at startup.
     - Asks for notification permission (Android 13+ runtime prompt).
     - Subscribes every install to the FCM topic "all_users".
     - Shows pushes in all app states (foreground, background, terminated).
     - When a notification is tapped, it opens the in-app Notifications
       screen, which routes to the referenced content (post, podcast, e-book,
       support, ...).

  b) Backend (Node/Express "admin-app")
     - Uses the Firebase Admin SDK with a service-account key.
     - When an admin sends a notification, the backend first saves it as a
       row in the Supabase table "mobile_notifications". It then pushes that
       row to the "all_users" FCM topic.

Key design decisions (keep these unless you have a strong reason not to):

  - TOPIC-BASED, NOT PER-DEVICE. The app has no per-user authentication, so
    every notification is a global broadcast. The backend never stores or
    uses device tokens. It sends to the topic "all_users", which every
    install subscribes to on startup. The FCM token is fetched only for
    diagnostics (debug log).
  - The in-app Notifications list (Supabase table mobile_notifications) is
    the source of truth. The push is a delivery mechanism on top of it.
  - Personal notification types (support_ticket, support_feedback) are
    saved in-app only and are NEVER pushed. A topic push would put one
    user's private message on every device's lock screen.
  - A push failure never fails the admin action. The in-app notification is
    already saved, and the API response reports the push status separately.
  - Android only. There is no iOS Firebase config or APNs setup yet. The
    code has iOS-safe branches, but iOS delivery has not been set up or
    tested.

4.7 Android 13+ POST_NOTIFICATIONS
----------------------------------
On Android 13 (API 33) and newer, notifications are blocked until the user
grants the runtime permission. Two things are required:
  1. The <uses-permission android:name="android.permission.POST_NOTIFICATIONS"/>
     line in the manifest (4.4).
  2. A runtime request. FirebaseMessaging.instance.requestPermission(...)
     shows the system prompt on Android 13+ (section 5).
On Android 12 and below, notifications are allowed by default.

5.1 Top-level background handler (REQUIRED to be top-level)
-----------------------------------------------------------

  @pragma('vm:entry-point')
  Future<void> firebaseBackgroundMessageHandler(RemoteMessage message) async {
    try {
      await Firebase.initializeApp(
          options: DefaultFirebaseOptions.currentPlatform);
    } catch (_) {
      // Already initialized in this isolate.
    }
    debugPrint('[FCM Background] id=${message.messageId} data=${message.data}');
  }

  - It runs in a separate isolate when the app is in the background or
    terminated.
  - It must NOT show a local notification. Backend pushes always contain a
    "notification" block, which Android already displays in the tray in
    those states. Showing one here would make every push appear twice.
  - @pragma('vm:entry-point') keeps release-mode tree shaking from removing
    it.

5.3 initialize() - the order matters
-------------------------------------
Call it once from main(), after Firebase.initializeApp() succeeds. Every
step is wrapped in its own try/catch (_guard), so one failure (for example,
no network for the token) does not skip the rest. Slow steps (permission
dialog, token, topic) run un-awaited, so they never delay startup.

  static Future<void> initialize() async {
    if (_initialized) return;
    _initialized = true;

    // 1. Background handler
    FirebaseMessaging.onBackgroundMessage(firebaseBackgroundMessageHandler);

    // 2. Local notifications plugin + Android channel
    await _guard('local notifications setup', _initLocalNotifications);

    // 3. Listeners
    FirebaseMessaging.onMessage.listen(_handleForegroundMessage);
    FirebaseMessaging.onMessageOpenedApp
        .listen((message) => _handleTap(message.data));   // background tap
    _messaging.onTokenRefresh.listen(_onTokenRefresh);

    // 4. iOS only: let the OS present foreground pushes
    if (Platform.isIOS) {
      await _guard('foreground presentation options', () =>
          _messaging.setForegroundNotificationPresentationOptions(
              alert: true, badge: true, sound: true));
    }

    // 5. Cold start: app launched by tapping a notification while terminated
    await _guard('initial message', () async {
      final initialMessage = await _messaging.getInitialMessage();
      if (initialMessage != null) _handleTap(initialMessage.data);
    });
    // ...or by tapping a LOCAL notification (foreground push) after the app
    // was killed
    await _guard('local notification launch details', () async {
      final details = await _localNotifications.getNotificationAppLaunchDetails();
      if (details?.didNotificationLaunchApp ?? false) {
        _handleTap(_decodePayload(details!.notificationResponse?.payload));
      }
    });

    // 6. Permission, token, topic subscription (network/user dependent)
    unawaited(_requestPermissionAndSubscribe());
  }

  static Future<void> _guard(String step, Future<void> Function() body) async {
    try { await body(); } catch (e) { debugPrint('[FCM] $step failed: $e'); }
  }

5.4 Local notifications + channel
---------------------------------

  static Future<void> _initLocalNotifications() async {
    const settings = InitializationSettings(
      android: AndroidInitializationSettings(_smallIcon),
      iOS: DarwinInitializationSettings(          // permission comes from FCM
        requestAlertPermission: false,
        requestBadgePermission: false,
        requestSoundPermission: false,
      ),
    );
    await _localNotifications.initialize(
      settings,
      onDidReceiveNotificationResponse: (response) =>
          _handleTap(_decodePayload(response.payload)),   // foreground-push tap
    );
    await _localNotifications
        .resolvePlatformSpecificImplementation<
            AndroidFlutterLocalNotificationsPlugin>()
        ?.createNotificationChannel(_channel);
  }

5.5 Permission, token and all_users topic subscription
------------------------------------------------------

  static Future<void> _requestPermissionAndSubscribe() async {
    await _guard('permission request', () async {
      // Android 13+: shows the POST_NOTIFICATIONS runtime prompt
      final settings = await _messaging.requestPermission(
          alert: true, badge: true, sound: true);
      debugPrint('[FCM] Permission status: ${settings.authorizationStatus}');
    });
    await _guard('token fetch', () async {
      fcmToken = await _messaging.getToken();
      _logToken('FCM token', fcmToken);
    });
    await _subscribeToAllUsers();
  }

  // Idempotent, so it runs on every start and after every token refresh.
  // Retries with backoff (10s, 60s), e.g. for a first launch while offline.
  static Future<void> _subscribeToAllUsers() async {
    const retryDelays = [Duration(seconds: 10), Duration(seconds: 60)];
    for (var attempt = 0;; attempt++) {
      try {
        await _messaging.subscribeToTopic(allUsersTopic);
        debugPrint('[FCM] Subscribed to topic "$allUsersTopic"');
        return;
      } catch (e) {
        debugPrint('[FCM] Subscribe to "$allUsersTopic" failed '
            '(attempt ${attempt + 1}): $e');
        if (attempt >= retryDelays.length) return;
        await Future.delayed(retryDelays[attempt]);
      }
    }
  }

  static void _onTokenRefresh(String newToken) {
    fcmToken = newToken;
    _logToken('FCM token refreshed', newToken);
    unawaited(_subscribeToAllUsers());
  }

  _logToken prints the full token only in debug builds (kDebugMode), for
  sending a single-device test from the Firebase Console. Release builds log
  only a 12-character prefix. The token is never sent to any server.

5.6 Foreground message handling
-------------------------------
Android never shows FCM notifications while the app is in the foreground, so
the app shows the notification itself:

  static void _handleForegroundMessage(RemoteMessage message) {
    onMessageReceived.value = message;
    NotificationBadge.instance.refresh();        // refresh in-app bell count

    if (!Platform.isAndroid) return;

    final messageId = message.messageId;
    if (messageId != null && !_shownMessageIds.add(messageId)) return; // de-dupe

    final title = message.notification?.title ?? message.data['title'];
    final body  = message.notification?.body  ?? message.data['body'];
    if ((title == null || title.isEmpty) && (body == null || body.isEmpty)) return;

    unawaited(_guard('show local notification', () {
      return _localNotifications.show(
        (messageId ?? DateTime.now().toIso8601String()).hashCode,
        title,
        body,
        NotificationDetails(
          android: AndroidNotificationDetails(
            _channel.id, _channel.name,
            channelDescription: _channel.description,
            importance: Importance.high,
            priority: Priority.high,
            icon: _smallIcon,
            color: const Color(0xFFD30814),      // = @color/notification_color
            styleInformation: BigTextStyleInformation(body ?? ''),
          ),
        ),
        payload: jsonEncode(message.data),       // carried to the tap handler
      );
    }));
  }

  static Map<String, dynamic> _decodePayload(String? payload) {
    if (payload == null || payload.isEmpty) return {};
    try { return Map<String, dynamic>.from(jsonDecode(payload) as Map); }
    catch (_) { return {}; }
  }

  (NotificationBadge is the app's existing unread-count ChangeNotifier in
  lib/notification_service.dart. Replace it with your repo's equivalent, or
  drop the call if you don't have one.)

5.7 Tap handling (all three entry points end here)
--------------------------------------------------
Entry points:
  - onMessageOpenedApp          : system-tray tap while app is in background
  - getInitialMessage()         : system-tray tap that launched a killed app
  - local notification response / getNotificationAppLaunchDetails()
                                : tap on a foreground-shown local notification

  static void _handleTap(Map<String, dynamic> data) {
    _pendingTap = {
      'id': data['notification_id'],
      'type': data['type'],
      'referenceId': data['reference_id'],
      'referenceType': data['reference_type'],
    };
    _openPendingTap();
  }

  // Called from the home screen's initState/dispose. A tap is only acted on
  // once the user is past splash/login.
  static void homeScreenMounted()   { _homeScreensMounted++; _openPendingTap(); }
  static void homeScreenUnmounted() { if (_homeScreensMounted > 0) _homeScreensMounted--; }

  static void _openPendingTap() {
    final tap = _pendingTap;
    if (tap == null || _homeScreensMounted == 0) return;
    _pendingTap = null;
    // Deferred: homeScreenMounted() runs inside initState, while the
    // navigator is still mid-build and can't accept a push.
    scheduleMicrotask(() {
      final navigator = navigatorKey.currentState;
      if (navigator == null) { _pendingTap = tap; return; }
      navigator.push(MaterialPageRoute(
        builder: (_) => NotificationsScreen(openNotification: tap),
      ));
    });
  }

Why the "pending tap" mechanism exists: on a cold start, main() handles
getInitialMessage() before any screen exists. After that, the splash screen
calls pushReplacement, which would destroy a screen pushed too early. Storing
the tap and opening it only once the home screen has mounted makes cold-start
taps reliable.

7. NOTIFICATION SCREEN / TAP ROUTING
================================================================================

Every tap opens NotificationsScreen (reference: lib/profile.dart) with the
tap payload. That screen then reuses its existing per-type row-tap logic, so
a pushed notification and an in-app list row are handled identically.

  class NotificationsScreen extends StatefulWidget {
    /// Push-tap payload: {id, type, referenceId, referenceType}
    final Map<String, dynamic>? openNotification;
    const NotificationsScreen({super.key, this.openNotification});
    ...
  }

  // State:
  @override
  void initState() {
    super.initState();
    _loadNotifications().then((_) => _openPushNotification());
  }

  void _openPushNotification() {
    final pushed = widget.openNotification;
    if (!mounted || pushed == null || pushed['type'] == null) return;
    final id = pushed['id']?.toString();
    // Prefer the loaded row (so its read state updates in the list); fall
    // back to the push payload if it isn't in the list.
    final item = _notifications.firstWhere(
      (n) => id != null && n['id']?.toString() == id,
      orElse: () => Map<String, dynamic>.from(pushed),
    );
    _onNotificationTap(item);
  }

_onNotificationTap(item) first marks the notification as read (Supabase
update + badge refresh). It then switches on
NotificationType.fromDbValue(item['type']):

  type (DB / FCM value)  Destination in the reference app
  ---------------------  ---------------------------------------------------
  community_post         Fetch post by reference_id -> CommunityScreen with
                         that post highlighted
  podcast_series         Fetch series -> PodcastSeriesDetailScreen(seriesId)
  podcast_episode        Fetch episode -> start playback
                         (PodcastPlayerController.loadAndPlay) + PodcastScreen
  ebook_book             Fetch book -> BookDetailsScreen(book)
  ebook_banner           EBooksLibraryScreen
  support_faq            (validate FAQ if reference_id given) ->
                         SupportCenterScreen
  support_ticket         SupportCenterScreen   (in-app only; never pushed)
  support_feedback       SupportCenterScreen   (in-app only; never pushed)
  null / unknown         No navigation - the user just stays on the
                         Notifications list

If a referenced item is missing or deleted, a SnackBar shows "Content not
found or removed." Any exception is caught, logged and shown the same way,
so a bad payload never crashes the app.

FCM data payload keys (all string values - FCM requires strings):
  notification_id  -> mobile_notifications.id
  type             -> mobile_notifications.type
  reference_id     -> mobile_notifications.reference_id
  reference_type   -> mobile_notifications.reference_type
Keys whose value is null are omitted, so the app reads them as null.

To add a NEW notification type:
  1. Add the enum value (section 8).
  2. Add it to the DB CHECK constraint.
  3. Add a case in _onNotificationTap.
Put routing in NotificationsScreen only, never in the FCM service.

8. NOTIFICATION TYPE ENUM

File in the reference repo: lib/notification_service.dart

  enum NotificationType {
    communityPost('community_post'),
    podcastSeries('podcast_series'),
    podcastEpisode('podcast_episode'),
    ebookBook('ebook_book'),
    ebookBanner('ebook_banner'),
    supportFaq('support_faq'),
    supportTicket('support_ticket'),
    supportFeedback('support_feedback');

    const NotificationType(this.dbValue);

    /// Exact string stored in the database and sent as FCM `data.type`.
    final String dbValue;

    /// Exact-match lookup; returns null for anything that isn't one of the
    /// database values (e.g. a Firebase Console test, or a typo).
    static NotificationType? fromDbValue(String? value) {
      for (final type in values) {
        if (type.dbValue == value) return type;
      }
      return null;
    }
  }

Mapping:
  communityPost   -> community_post
  podcastSeries   -> podcast_series
  podcastEpisode  -> podcast_episode
  ebookBook       -> ebook_book
  ebookBanner     -> ebook_banner
  supportFaq      -> support_faq
  supportTicket   -> support_ticket
  supportFeedback -> support_feedback

Handling unknown types safely:
  - fromDbValue returns null (never throws) for an unknown, empty or
    missing type.
  - The switch in _onNotificationTap has an explicit "case null:" that does
    nothing. The user stays on the Notifications list, and there is no crash
    and no error message.
  - _openPushNotification returns early when type is null, so a push with no
    type (for example the Git Bash test in section 11, or a Firebase Console
    test) just opens the Notifications list.
  - Never use NotificationType.values.byName() or firstWhere without orElse.
    Both throw on unknown input.

The database must allow exactly the same strings. In the Supabase table
mobile_notifications:

  type VARCHAR(50) NOT NULL DEFAULT 'community_post'
    CONSTRAINT mobile_notifications_type_check
    CHECK (type IN ('community_post', 'podcast_series', 'podcast_episode',
                    'ebook_book', 'ebook_banner', 'support_faq',
                    'support_ticket', 'support_feedback')),

The reference repo also has a Dart test (test/notification_type_test.dart)
that checks the enum and the SQL list stay in sync. Adding an equivalent is
recommended.

Full table (for reference):

  CREATE TABLE IF NOT EXISTS mobile_notifications (
    id UUID DEFAULT gen_random_uuid() PRIMARY KEY,
    title VARCHAR(255) NOT NULL,
    message TEXT NOT NULL,
    type VARCHAR(50) NOT NULL DEFAULT 'community_post' CONSTRAINT ... (above),
    reference_id UUID,
    reference_type VARCHAR(50),
    is_read BOOLEAN NOT NULL DEFAULT false,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
  );

9.3 The push service (single source of push logic)
--------------------------------------------------
File: admin-app/services/pushService.js
Exports: sendNotificationPush(notificationRow), ALL_USERS_TOPIC

Constants (must match the app):
  ALL_USERS_TOPIC    = 'all_users'
  ANDROID_CHANNEL_ID = 'tbt_notifications'
  ANDROID_ICON       = 'ic_stat_notification'
  ANDROID_COLOR      = '#D30814'
  PERSONAL_TYPES     = support_ticket, support_feedback  (never pushed)

Behavior:
  - Lazy, one-time initialization: it loads the service account from
    FIREBASE_SERVICE_ACCOUNT_JSON or FIREBASE_SERVICE_ACCOUNT_PATH, then
    calls:
        const app = initializeApp({ credential: cert(serviceAccount) }, 'tbt-push');
        messaging = getMessaging(app);
    It logs: [push] Firebase Admin initialized for project "mobile-app-d8c0f"
  - If the JSON fails to parse, the error message deliberately does NOT
    include the parser's message, because that could quote part of the
    private key.
  - The message it sends:

      await messaging.send({
        topic: 'all_users',
        notification: { title: row.title, body: row.message },
        data: {                       // strings only; null keys omitted
          notification_id, type, reference_id, reference_type
        },
        android: {
          priority: 'high',
          notification: {
            channelId: 'tbt_notifications',
            icon: 'ic_stat_notification',
            color: '#D30814',
          },
        },
        apns: { payload: { aps: { sound: 'default' } } },
      });

  - It NEVER throws. It returns one of:
        { sent: true,  messageId: 'projects/mobile-app-d8c0f/messages/<id>' }
        { sent: false, reason: 'push not configured' | '"<type>" notifications
                                are in-app only' | '<firebase error code>' }

The top of pushService.js looks like this:

  const fs = require('fs');
  const path = require('path');
  const { initializeApp, cert } = require('firebase-admin/app');
  const { getMessaging } = require('firebase-admin/messaging');

The service lives in admin-app/services/, so a relative
FIREBASE_SERVICE_ACCOUNT_PATH is resolved with
path.resolve(__dirname, '..', filePath), i.e. relative to admin-app/.

10. ADMIN PUSH FLOW
================================================================================

  Admin clicks "Send notification" in the admin panel
      -> POST /api/admin/<area>/<id>/send-notification
  Backend validates the item (e.g. a community post must be approved)
      -> INSERT a row into Supabase mobile_notifications
         (title, message, type, reference_id, reference_type)
  Backend calls sendNotificationPush(insertedRow)
      -> Firebase Admin SDK messaging.send({ topic: 'all_users', ... })
  FCM accepts the message and returns a message ID
      -> FCM fans it out to every device subscribed to "all_users"
  Android devices receive the notification
      (tray when background/closed; local notification when foreground)
  User taps it -> NotificationsScreen -> per-type route (section 7)
  The in-app Notifications list also shows the row (source of truth)

Send-notification routes in the reference server.js:
  POST /api/admin/community/posts/:id/send-notification   type community_post
  POST /api/admin/podcast/series/:id/send-notification    type podcast_series
  POST /api/admin/podcast/episodes/:id/send-notification  type podcast_episode
  POST /api/admin/ebooks/books/:id/send-notification      type ebook_book
  POST /api/admin/ebooks/banner/:id/send-notification     type ebook_banner
  POST /api/admin/support/faqs/:id/send-notification      type support_faq
  POST /api/admin/support/tickets/:id/send-notification   type support_ticket   (in-app only)
  POST /api/admin/support/feedback/:id/send-notification  type support_feedback (in-app only)

Each route follows the same pattern:

  const { data, error } = await supabase
    .from('mobile_notifications')
    .insert([{ title, message, type: '<type>', reference_id: item.id,
               reference_type: '<ref_type>' }])
    .select();
  if (error) throw error;
  const push = await sendNotificationPush(data[0]);
  res.status(201).json({ success: true, notification: data[0], push });

The "push" field in the response shows the push result without failing the
request.

11.1 The script: admin-app/scripts/send-test-push.js
----------------------------------------------------

  // Sends a one-off test FCM push to every installed app (the `all_users`
  // topic), to check the push pipeline end to end from a terminal.
  //
  // Usage, from admin-app/:
  //   node scripts/send-test-push.js                   default title/body
  //   node scripts/send-test-push.js "Title" "Body"    custom title/body
  //
  // Reuses services/pushService.js (same credentials from .env, same topic,
  // channel and payload shape as real notifications). It does NOT create a
  // mobile_notifications row, so nothing appears in the in-app Notifications
  // list; tapping the push just opens that list.

  require('dotenv').config({ path: require('path').join(__dirname, '..', '.env') });
  const { sendNotificationPush, ALL_USERS_TOPIC } = require('../services/pushService');

  const title = process.argv[2] || 'TBT Test Notification';
  const body = process.argv[3] || 'Hello! This is a test push notification from Git Bash.';

  (async () => {
    console.log(`Sending test push to FCM topic "${ALL_USERS_TOPIC}"...`);
    console.log(`  Title: ${title}`);
    console.log(`  Body:  ${body}`);

    // No `type`, so the app treats a tap as "open the Notifications list".
    const result = await sendNotificationPush({
      id: `test-${Date.now()}`,
      title,
      message: body,
    });

    if (result.sent) {
      console.log(`\nSUCCESS: Firebase Cloud Messaging accepted the push.`);
      console.log(`  FCM message id: ${result.messageId}`);
      process.exit(0);
    }
    console.error(`\nFAILED: push was not sent (${result.reason}).`);
    console.error('  Check FIREBASE_SERVICE_ACCOUNT_PATH in admin-app/.env and the error logged above.');
    process.exit(1);
  })();

13. EXPECTED BEHAVIOR
================================================================================

App OPEN (foreground)
  - FCM delivers to FirebaseMessaging.onMessage. Android does NOT show it
    automatically.
  - The app shows a heads-up local notification on channel tbt_notifications
    (small icon ic_stat_notification, red accent #D30814, big-text style).
  - The in-app bell/unread badge refreshes.
  - The same message id is never shown twice.

App in BACKGROUND
  - Android shows the notification in the system tray itself, using the
    manifest defaults (channel, icon, color) and the payload's android
    block.
  - firebaseBackgroundMessageHandler runs and only logs. It must not show a
    second notification.

App FULLY CLOSED (terminated / swiped away)
  - Same as background: Android shows it in the tray.
  - Note: if the user FORCE-STOPS the app (Settings -> Apps -> Force stop),
    Android blocks all FCM delivery until the app is opened again. This is
    Android behavior, not a bug.

User TAPS the notification
  - Background: the app resumes, onMessageOpenedApp fires, and
    NotificationsScreen opens.
  - Terminated: the app cold-starts. getInitialMessage() returns the
    message, and the tap is stored as pending. After splash/login, the home
    screen mounts and NotificationsScreen opens.
  - Foreground (local notification): onDidReceiveNotificationResponse fires
    and NotificationsScreen opens.
  - NotificationsScreen then marks the row as read and routes by type
    (section 7). With no or an unknown type, the user stays on the list.

14. TROUBLESHOOTING
================================================================================

Notification permission
  - Android 13+: Settings -> Apps -> TBT -> Notifications must be ON. If the
    user denied the prompt, the app will not ask again. Enable it manually,
    or clear the app data and reinstall.
  - Check that the manifest has POST_NOTIFICATIONS.
  - Debug log: "[FCM] Permission status: AuthorizationStatus.authorized".

App launched at least once
  - A fresh install receives NOTHING until the app has been opened once,
    because that first launch is when it subscribes to all_users. Open it
    once with internet on, then test.

all_users topic subscription
  - Debug log should show: [FCM] Subscribed to topic "all_users"
  - If it shows "Subscribe ... failed", check the network. The app retries
    after 10s and 60s, and again on every app start.
  - Topic names are case-sensitive: all_users in the app AND the backend.

Firebase configuration
  - Log "Firebase initialization failed" means firebase_options.dart or
    google-services.json is missing or wrong. Run flutterfire configure
    again.
  - The project ID in the app config and in the service account must BOTH be
    mobile-app-d8c0f. A push sent from project A never reaches an app built
    with project B's config.

google-services.json
  - Must be at android/app/google-services.json.
  - package_name inside must equal applicationId (com.tbt.tbtmobileapp).
  - The com.google.gms.google-services plugin must be applied in
    android/app/build.gradle, with the classpath in android/build.gradle.

Firebase Admin credentials
  - "[push] Firebase service account not configured" means
    FIREBASE_SERVICE_ACCOUNT_PATH/JSON is not set, or .env was not loaded.
    Run from admin-app/.
  - "service-account file not found" means the path is wrong. A relative
    path is resolved against admin-app/.
  - "does not contain valid JSON" means the file is corrupted or truncated,
    or the inline JSON was not on one line.
  - messaging/invalid-credential or an auth error means the key was revoked
    or deleted. Generate a new key in the Firebase Console.
  - Confirm the log says: Firebase Admin initialized for project "mobile-app-d8c0f"

Android notification channel
  - Channel ID tbt_notifications must match in the manifest, Dart and the
    backend payload.
  - If the user turned the channel off (Settings -> Apps -> TBT ->
    Notifications -> TBT Notifications), nothing shows. Turn it on.
  - Channel settings are fixed once created. After changing importance,
    uninstall and reinstall (or use a new channel ID).
  - Icon is a white square: the small icon is not a white-on-transparent
    drawable (section 4.5).

Network
  - Phone: needs internet. Delivery can be delayed on metered or
    battery-saver networks.
  - Backend machine: needs outbound HTTPS to fcm.googleapis.com and
    oauth2.googleapis.com.

FCM message ID
  - If the script prints a message id (projects/mobile-app-d8c0f/messages/...),
    FCM ACCEPTED the message. From that point, delivery problems are on the
    device side: permission, subscription, force-stop, battery optimization.
  - If there is no message id, the problem is on the backend side:
    credentials, network, or project mismatch.
  - Topic sends are fire-and-forget. FCM does not report per-device delivery.
    Allow a few seconds, occasionally up to about a minute.

Background handler
  - It must be a TOP-LEVEL function with @pragma('vm:entry-point'),
    registered once through FirebaseMessaging.onBackgroundMessage.
  - Duplicate notifications in background/closed state mean the handler is
    showing a local notification. Remove that call.
  - No notifications in background at all: check that the manifest does not
    declare its own FirebaseMessagingService <service> (section 4.4).
  - Aggressive OEM battery savers (e.g. Xiaomi, Oppo, Vivo) can block
    background delivery. Set the app to "No restrictions" for battery.

Terminated-state handling
  - A tap from a killed app does nothing: check getInitialMessage() is
    called in initialize(), check navigatorKey is set on MaterialApp, and
    check that homeScreenMounted() is called from the home screen's
    initState.
  - The Notifications screen flashes and then disappears: it was pushed
    before the splash pushReplacement. Use the pending-tap mechanism
    (section 5.7).

Useful commands
  flutter clean && flutter pub get && flutter run      (fresh debug build)
  adb logcat | grep -E "FCM|flutter"                   (live device logs)

15. SECURITY
================================================================================

  - NEVER commit firebase-service-account.json. It grants full admin access
    to the Firebase project.
  - NEVER commit .env (admin-app/.env). It holds the Supabase service-role
    key and the Firebase credentials. Commit only .env.example, with
    placeholders.
  - NEVER expose private keys: do not paste them into chat, tickets,
    screenshots, logs or documentation. Do not print them from scripts.
  - NEVER share real FCM device tokens. The app prints the full token only
    in debug builds. Do not copy it into documents or tickets.
  - Do not put the service account in the Flutter app. The mobile app only
    ever gets the client config (google-services.json / firebase_options.dart).
  - If a key is ever committed or leaked: delete it immediately in Google
    Cloud Console -> IAM -> Service accounts -> Keys, generate a new one, and
    clean it out of the Git history. Deleting the file in a new commit is
    NOT enough.

  # Firebase Admin service-account keys (full project admin access — never commit).
  admin-app/firebase-service-account*.json

18. IMPORTANT NOTE FOR ANOTHER DEVELOPER
================================================================================

This documentation describes the implementation that was already
successfully tested in another TBT app repository. You must adapt file paths
and existing architecture to your repository instead of blindly overwriting
existing notification code.

In practice:
  - If your repo already has a notification service, a Notifications
    screen, or an unread badge, integrate this logic into them. Do not
    replace them wholesale.
  - Screen and class names in section 7 (CommunityScreen, PodcastScreen,
    BookDetailsScreen, SupportCenterScreen, NotificationBadge, ...) are from
    the reference repo. Map them to your equivalents.
  - Keep exactly ONE place that calls FirebaseMessaging.onBackgroundMessage,
    ONE place that creates the tbt_notifications channel, and ONE backend
    function that sends pushes (sendNotificationPush). Duplicates cause
    double notifications or behavior that drifts apart.
  - Keep these identifiers identical across app and backend: topic
    all_users, channel tbt_notifications, icon ic_stat_notification, the
    eight type strings, and the data keys notification_id / type /
    reference_id / reference_type.
  - Credentials are never part of this document. Get the Firebase
    service-account key from the Firebase Console yourself (or from your
    team's secret store), and keep it out of Git.
